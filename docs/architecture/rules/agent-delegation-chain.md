# 에이전트 위임과 서브에이전트 출력 처리

> 이 문서는 메인 Claude가 위임을 사전 승인받는 방식과, 서브에이전트 결과를 받은 뒤
> 무엇을 하는지를 설명합니다. **정본은 `plugins/common/rules/agent-delegation-chain.md`**
> (세션에 주입되는 룰)이다 — 이 문서는 그 정의를 **설명**하는 것이지 재정의가 아니다.

> **폐기 기록 (2026-08-27, W-022 R1)**: 이 문서는 원래 `---DELEGATION_SIGNAL---` 블록을
> 스캔해 `TYPE`/`TARGET` 필드로 다음 에이전트를 자동 호출하는 **순차 체인 모델**을
> 설명했다(과거 §2~§7 — 플로우 다이어그램, TYPE별 처리, 위임 중단 조건, 워크드 예시).
> 판별 결과 이 신호를 실제로 파싱하는 결정론적 코드는 어디에도 없었다. 유일한 소비
> 지점은 정본이 메인 Claude에게 준 **자연어 지시** — 파서가 아니라 모델 판단에 의존하는
> 경로였다. 게다가 오케스트레이션은 이미 스킬 주도 플랫 위임으로 넘어가 있었다.
>
> (조사를 촉발한 준수율 관측 "8종 중 6종 미준수"는 **교란돼 있어 판정 근거로 쓰지
> 않았다** — `implement-code` 시나리오의 `task.md`가 검사 대상 형식을 직접 지시했으므로
> 대조군이 아니었다. 트리거였을 뿐이다. `CLAUDE.md` → Delegation Signal 참고.) 신호 기계 계약(형식·TYPE→Action 매핑·자동 호출
> 절차)을 정본에서 폐기했고, 이 해설본도 그에 맞춰 정리했다. 상세 근거:
> `docs/specs/2026-08-27-delegation-signal-contract-review.md`(W-021).

> **leaf 에이전트는 중첩하지 않는다.** 네이티브 중첩 서브에이전트가 가능해도, 이 레포
> 스케일에서 leaf 중첩은 성능 이득 없이 예측불가능성·디버깅 부채만 더한다. 대규모 병렬은
> 네이티브 `ultracode`로 위임한다 (Spec 2 / W-006, `CLAUDE.md` → Orchestration Model).

## 0. 위임 사전 승인 (Standing Authorization)

주입 룰 최상단의 `Standing User Authorization for Delegation` 조항에 대한 해설이다.

**무엇을 선언하는가.** 이 프로젝트 사용자는 서브에이전트 위임을 세션 단위로 **사전
승인**했다. 요청이 `agents/`의 어느 `description`과 맞으면 그것은 "사용자가 AgentTool을
요청한 것"으로 간주한다. 재확인을 묻지 않고, 에이전트가 정의된 일을 메인이 인라인으로
처리하지 않는다.

**왜 명시가 필요했는가.** 2026-08-21 A/B 실측에서, 동일 과제·동일 레포·동일 버전 조건에서
메인 루프의 Agent 직접 호출이 승인문구 없이는 **0/3**, `--append-system-prompt`로 문단만
주입하면 **3/3**이었다. 표본이 작아(Fisher exact 단측 p=0.05, 경계값) 확정은 아니지만,
"에이전트가 정의돼 있는데 메인이 직접 처리한다"는 관찰이 재현된다는 점은 확인됐다.

**억제 원인은 아직 모른다.** Claude Code v2.1.219+가 서버사이드로 주입하는 프롬프트 섹션
`heron_brook`("Do not call the AgentTool unless the user requested it")이 유력 후보다 —
Opus 5 전용 게이트이고 문서화된 opt-out이 없다(anthropics/claude-code#80988). 다만 위
실측은 Sonnet 5 세션에서 돌아 그 문자열이 부재했으므로, **이 조항은 heron_brook이
원인이라는 전제 위에 서 있지 않다.** 원인이 무엇이든 위임 사전 승인은 이 레포의 의도된
정책이라 조항 자체는 독립적으로 성립한다.

**범위 가드 — 왜 무제한이 아닌가.** 조항을 무제한으로 두면 오타 한 줄 고치는 일까지
서브에이전트를 띄운다. 위임은 컨텍스트 왕복 비용이 있어서, 이득 없는 위임은 지연과 토큰만
쓴다. 그래서 인라인 예외를 **둘로만** 못박았다 — (1) 파일·심볼·값을 이미 아는 단일 조회,
(2) 한 파일 안의 기계적 수정(오타·포맷·import 정렬). 크기를 기준으로 삼지 않은 것은
의도적이다: 파일 하나짜리 코드 리뷰도 `review-code`가 해야 하는 일이고, 실제로 이번
실측에서 승인문구 주입 시 3/3 모두 그렇게 동작했다. 기준은 **분량이 아니라 전용 에이전트가
정의돼 있는 일인가**이다.

**선택 기준은 여기 없다.** 어느 에이전트를 고를지는 하네스가 시스템 프롬프트에 제공하는
에이전트 목록·`MUST USE when:` 트리거가 SSOT다(D-18 — `agent-system.md`의 키워드 매핑 표는
네이티브 재기술이라 제거됐다). 이 문서에 표를 복제하면 드리프트가 시작된다.

**층위를 혼동하지 말 것.** 이 조항은 모델 판단에 주는 **입력**이지 보장이 아니다.
반드시 일어나야 하는 검증은 Stop 훅(`plugins/common/hooks/stop-validator.py`,
공식 `{"decision":"block"}` 스키마)이 결정론적으로 강제한다. 규율을 프롬프트로만 세우면
같은 실패가 반복된다.

**재검증 조건.** 원인 규명을 위해서는 `claude -p --model opus`로 모델을 고정하고, 위임
트리거가 강한 과제(다중 파일 병렬 조사 등)로, n≥5에서 다시 측정해야 한다. 채점은 출력
텍스트가 아니라 트랜스크립트의 `tool_use` 이름을 세되, `cwd` 필터로 다른 프로젝트 세션의
오염을 제거한다.

## 1. 핵심 원칙

```
NEVER allow subagents to call other subagents.
ALWAYS have main Claude manage the delegation chain directly.
```

**왜 메인 Claude가 직접 관리해야 하는가?**

- 서브에이전트가 또 다른 서브에이전트를 호출하면 무한 재귀 위험
- 위임 체인의 상태(현재 어느 단계인지)를 추적하는 단일 주체가 필요
- 사용자 개입이 필요한 P0 상황을 감지할 수 있는 곳은 메인 Claude뿐

## 2. 서브에이전트 출력을 받았을 때

정본의 `On Receiving Subagent Output` 절에 대한 해설이다.

**핵심 관점 전환.** 서브에이전트 출력은 **읽고 판단할 결과물**이다. 과거 모델(위 폐기
기록 참고)은 출력 안의 신호 필드가 다음 단계를 결정했다 — 지금은 그 반대다: **다음
단계의 순서는 호출한 스킬(예: `auto-dev`)이 정한다.** 출력은 그 스킬이 다음 판단을
내리기 위해 읽는 입력일 뿐, 자기 자신 안에 다음 행동 지시를 담고 있지 않다.

**절차 (정본 그대로):**

1. 출력을 읽고 완료 여부·품질을 판단한다.
2. P0 모호성이 있으면 사용자에게 선택지를 제시하고 답을 받는다(호스트가 제공하는 수단으로 —
   D-25: 특정 툴 이름을 하드코딩하지 않는다, 헤드리스·비대화형 호스트엔 그 툴이 없다).
   이 항목은 옛 모델에서도 동일했다 — 신호 유무와 무관하게 항상 참이다.
3. 다음 에이전트 호출 여부·대상은 호출한 스킬의 절차를 따른다. `auto-dev`라면 그 스킬의
   Step 순서(Development → Validation 등)가 SSOT다. 서브에이전트 출력 안의 특정 문자열을
   파싱해 분기하지 않는다.
4. 체인(또는 병렬 dispatch)이 끝나면 사용자에게 요약을 보고한다.

**P0 모호함이란? (여전히 유효한 예시)**

```
- 데이터 무결성에 영향: "삭제 시 관련 데이터도 삭제하나요?"
- 보안 정책: "관리자만 접근 가능한가요, 모든 인증 사용자가 접근 가능한가요?"
- 금융/비용 계산: "할인이 중복 적용되나요?"
- 핵심 비즈니스 분기: "재고 없을 때 주문을 받나요, 막나요?"
```

**병렬 dispatch에서는 무엇이 다른가.** 스킬 주도 플랫 위임(`CLAUDE.md` → Orchestration
Model, Spec 2/W-006)에서는 메인이 여러 에이전트를 동시에 dispatch하고 결과를 모아
판단한다 — 순차 체인처럼 "이전 출력의 신호가 다음 호출을 트리거"하는 구조가 아니다.
이 절이 순차 호출을 전제하지 않는 것은 그래서다.

## 3. 체인 관련 Anti-Patterns

```
# 잘못된 예 1: 서브에이전트가 서브에이전트 호출
implement-code 내부에서:
  Task("fix-bugs", ...)  ← 금지! disallowedTools: [Task]

# 잘못된 예 2: P0 모호함 무시하고 다음 단계로 진행
P0: "결제 오류 시 환불 정책 미정의"
→ (P0 해결 없이) implement-code 호출  ← 위험! P0 해결 없이 구현 시작

# 잘못된 예 3 (폐기된 패턴): 서브에이전트 출력의 특정 문자열을 파싱해 분기
if "DELEGATE_TO" in output: call_agent(...)  ← 폐기 — 스킬이 다음 단계를 정한다

# 올바른 예: P0 항상 우선, 다음 단계는 스킬이 정한다
P0 발견 → 사용자에게 질문 → 답변 수신 → 호출한 스킬의 다음 단계 진행
```
