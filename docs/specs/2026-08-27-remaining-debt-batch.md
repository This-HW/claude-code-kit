## 4. 설계 결정 (단정. 구현 세션이 재결정하지 않는다)

### 4.1 R8 — 예방이 탐지보다 낫다

v2.15.0에서 `.claude-plugin/plugin.json` 만 올리고 생성물을 재생성하지 않아 §14가 잡았다.
superpowers는 `.version-bump.json` 팬아웃으로 **사전 예방**한다.

**우리 매니페스트는 생성물이므로 팬아웃이 아니라 재생성이 정답이다.**
→ `scripts/bump-version.sh` 신설: 버전 인자를 받아 SSOT를 갱신하고 **곧바로 `build-targets.py --write` 를
호출**한 뒤 `--check` 로 자기 결과를 검증한다. 사람이 두 단계를 기억할 필요를 없앤다.
추가로 **낡은 버전 문자열 감사**(superpowers의 `audit.exclude` 상당)를 붙인다 — 문서에 박제된
옛 버전을 잡는다.

### 4.2 R7 — 하네스별로 "필요한 만큼만" 준다. 일괄 링크가 아니다

superpowers 실측이 근거다: `AGENTS.md`→`CLAUDE.md` 심링크, 그러나 `GEMINI.md` 는 **부트스트랩
import 두 줄짜리 별도 파일**. 하네스마다 최적 형태가 다르다.

**CCK의 제약이 하나 더 있다**: `CLAUDE.md`(프로젝트 지침)와 `AGENTS.md`(rules 생성물)는 **내용이 다르고**
`AGENTS.md` 는 `export_harness.py` 가 마커 블록을 교체하는 **생성물**이다. 그래서 단순 심링크는 불가다.

**결정**:
- `AGENTS.md` 는 **생성물로 유지**한다 (마커 블록 = rules). 심링크로 만들지 않는다
- `CLAUDE.md` 는 **사람이 쓰는 프로젝트 지침으로 유지**한다
- **중복 제거는 "호스트 중립 프로젝트 규약"을 SSOT 한 곳으로 빼서** 달성한다:
  `docs/conventions/*.md` → `CLAUDE.md` 는 `@` import, `AGENTS.md` 는 생성기가 **두 번째 마커 블록으로 인라인**
  (다른 하네스는 `@` import를 이해하지 못하므로 인라인이 필수)
- Claude Code 세션은 rules를 **훅으로 이미 받는다** → `CLAUDE.md` 가 `AGENTS.md` 를 import하면 **이중 주입**이다. 금지
- **크기 상한 (2026-08-27 조사 후 정정)**: Codex `project_doc_max_bytes` 는 **파일당이 아니라
  병합 총량**이고(글로벌 `~/.codex/AGENTS.md` → git root → cwd 순으로 붙이다 상한에서 멈춘다),
  **초과분은 경고 없이 사라진다**. 따라서:
  - **"하위 디렉토리로 분할"은 우회로가 못 된다** — 오버플로를 아래로 밀면 그게 먼저 잘린다
  - 상한은 소비자의 **글로벌 파일까지 합산**이므로 우리 파일이 32 KiB를 다 쓰면 안 된다
  - → 게이트 상한은 **24,576 B (32 KiB의 75%)**. 나머지 8 KiB는 소비자 글로벌 몫으로 남긴다
  - 조용히 잘리므로 **우리 게이트가 유일한 방어선**이다
  근거: `docs/research/2026-08-27-superpowers-distribution.md` 부록 1

### 4.3 R9 — 검증할 수 없는 타겟은 싣지 않는다

superpowers는 9종을 싣지만, 그 프로젝트는 새 하네스 지원에 **수용 테스트 트랜스크립트**를 요구한다.
우리에게는 `codex`·`agy` 만 로컬에 있다.

**결정: 로컬에서 실물 검증이 불가능한 타겟은 활성화하지 않는다.**
Antigravity `agents/` 건에서 확립한 원칙("깨진 컴포넌트를 실은 채 지원한다고 광고하지 않는다")의 연장이다.
대신 **각 타겟의 공식 규격을 1차 자료로 조사해 `packaging/targets.json` 에 `enabled:false` + 규격 요약 +
활성화 조건(무엇이 확보되면 켜는가)을 기록**한다. 이것이 R9의 완료 형태다.

### 4.4 R6 — 게이트 통합은 **하지 않는다** (근거 있는 폐기)

§11·§13·§14가 모두 "생성물이 SSOT와 일치하는가"이지만 **입력·판정 기준·실패 메시지가 전부 다르다**
(sha 대조 / 집합 대조 / 파일 존재+내용 대조). 공통화하면 추상이 세 케이스를 다 감당하지 못해
분기 파라미터가 늘고, 게이트 코드가 어려워진다 — **게이트는 읽기 쉬워야 신뢰된다.**

대신 **공통으로 지켜야 할 규약을 문서화**한다(이미 `CLAUDE.md` 경로 봉쇄 관례로 착수). 네 번째
드리프트 게이트가 필요해지는 시점에 재검토한다. **이 판단을 문서에 남기는 것이 R6의 완료다.**

### 4.5 R3 — 20종을 억지로 채우지 않는다. **평가 가능성으로 분류**한다

W-018 스펙이 이미 경고했다: "저품질 시나리오 양산 — 통과가 보장된 껍데기는 커버리지가 아니라 착시".
티어2 20종에는 `clarify-requirements`(AskUserQuestion 의존), `facilitator-teams`(message/broadcast),
`synthesizer`·`consensus-builder`(다른 에이전트 출력을 입력으로 받음) 처럼 **단독 시나리오로 재현할 수 없는**
것들이 섞여 있다.

**결정**: 20종을 **평가 가능 / 조건부 / 불가**로 분류하고 근거를 남긴다. 평가 가능한 것만 시나리오를 만든다.
**분류 자체가 산출물**이며, "불가"에는 무엇이 갖춰지면 가능해지는지를 적는다.

### 4.6 R1 — 판별 후 **실행까지** 한다

W-021 스펙의 판별 조건(스킬이 DELEGATION_SIGNAL을 실제로 파싱하는가)을 실행하고,
결과에 따라 **계약 유지(정의 수정) 또는 폐기(§12 검사·33개 정의의 관련 절 제거)** 중 하나를 **실제로 수행**한다.

## 8. 배치 중 발견 — `§9 test-ratchet` 의 마스킹 구멍 (2026-08-27, 기획 세션)

**발견 경위**: R8의 감사 도구를 폐기하기로 판정하면서 "테스트 14건이 줄어드는데 §9가 잡을까"를 물었다.
답은 **잡지 못한다**였고, 이유가 게이트 설계에 있다.

### 사실 — 실패 모드가 둘이고, 두 번째가 더 근본적이다
`§9` 는 비교 기준을 `git merge-base main HEAD` 로 잡는다(폴백: `origin/main` → `HEAD~1`).
즉 **브랜치 전체의 순증감**만 본다. 여기서 두 가지가 새어 나간다.

**(A) 순증감 마스킹** — 먼저 추가하고 나중에 지우면 net이 양수라 green.

**(B) 생애주기 은닉 — 이쪽이 더 근본적이다.** 파일이 **base 이후에 생겼다가 HEAD 전에 지워지면**
base 시점에도 없고 HEAD 시점에도 없다. `git diff base HEAD` 에 **그 파일이 아예 나타나지 않는다.**
순증감이 상쇄되는 게 아니라 **관측 자체가 안 된다.**

> 실측(2026-08-27): `scripts/tests/test_audit_version_strings.py` 는 `a630ab3` 에서 신설되고
> `102d568` 에서 삭제됐다. 두 커밋 모두 base 이후다.
> `git diff 017ee39 HEAD -- <그 파일>` → **0건**. 반면 `git show 102d568` 단독으로는
> **추가 0 / 삭제 36** 이 명확히 보인다.
>
> (이 정정은 구현 세션의 보고에서 나왔다. 나는 (A)만 상정했고 (B)를 놓쳤다.)

```
우리 통합 브랜치 base = 017ee39 (v2.15.0 직전)
브랜치 안에서: 테스트 +41 (360 → 401) … 그다음 -14 (감사 도구 폐기)
→ net +27 → green. 14건이 삭제된 사실은 보이지 않는다
```

### 왜 문제인가
이 프로젝트의 실제 워크플로는 **25+ 커밋 장기 통합 브랜치**다(트랙 병렬 + Stage 분할).
그 안에서 테스트를 먼저 추가하고 나중에 지우면 **어떤 삭제도 게이트에 걸리지 않는다.**
즉 §9는 "PR 단위 순감소"는 막지만 **"브랜치 내부 삭제"는 구조적으로 못 본다.**

게이트가 있다는 사실이 방어를 보증하지 않는다 — 이 배치가 §11/§13/§14에서 반복 확인한 것과 같다.

### 판정: 이번 배치에서 고친다. 단 **통합 시점에**
`scripts/verify-done.sh` 는 두 트랙이 공유하는 파일이라, 트랙 진행 중에 내가 손대면 충돌을 만든다.
**두 트랙이 착지한 뒤 통합 단계에서 기획 세션이 직접 수정**한다.

수정 방향(구현 시 재확인):
- base 대비 순증감 검사는 **유지**한다(PR 관점에서 유효하다)
- **추가로** base..HEAD 범위의 **각 커밋**을 훑어 `TEST-RATCHET-ALLOW` 마커 없이 테스트/assert가
  줄어든 커밋이 있으면 fail. (A)의 상쇄와 (B)의 은닉을 **둘 다** 드러낸다 —
  커밋 단위로 보면 생애주기가 구간 안에 있어도 삭제 커밋 자체는 보인다
- 마커는 **커밋 메시지**에서 찾는다. 기존 구현은 `TEST-RATCHET-ALLOW` 가 diff 아무 곳에나 있으면
  검사 전체를 껐다 — 무관한 파일의 한 줄로 게이트를 무력화할 수 있었다(같은 날 발견한 두 번째 구멍)
- 이번 배치의 감사 도구 폐기 커밋은 **정당한 삭제**이므로 그 커밋에 마커를 요구한다 —
  마커가 있으면 통과, 없으면 fail. **정당성을 커밋에 남기게 하는 것이 이 게이트의 목적**이다
